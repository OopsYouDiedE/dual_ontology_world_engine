结论：现有 Core 可以组合“多人在岗时提交一次共同效果”，本轮已用正式 Core 公共接口证明；宿主目前的夜间结算没有检查共同在岗时间，议事结算也没有实际提交群体动作。另有一个可独立修正的宿主错误：某条邀约请求保留了无法在接收者上下文绑定的 `Target` 槽，社交接受后仍不会产生行动候选。不能把这些问题统称为“Core 缺少同步调度”。

## 2. 占用、共同时间与最小合作反例

`Fx.SeizeAt` 在一个阶段检查本岗位未占用，设置 `Occupied/Prying`，等待三刻，再设置 `Worked` 并清除占用。三个岗位各自独立执行。`NightBegins` 每夜清零 `Worked/_seizeOk`，因此不是跨夜累计；但 `Council.Seizure` 仍仅要求每站本夜 `Worked > 0` 且成功演员集合中有人对应该站，没有共同时间交集、同步版本或连续保持条件（`GameJobs.cs:113–115`，`Morning.cs:199–208`，`Council.cs:55–81`）。

中性正式 Core 实测 A、B、C 的占用区间分别为 `[0.3,3.3]`、`[4.6,7.6]`、`[8.9,11.9]`，共同交集为空，最终 `Worked=[1,1,1]`、`Occupied=[0,0,0]`。这证明“历史都完成过”与“曾共同在岗”不同。把该输入与宿主上述静态判据对照，并补足各演员的岗位与入口资格，该判据仍为真。**这里没有执行正式章节或替代宿主结算器；结论是公共 Core 实测轨迹加静态判据反例。** 是否必须共同保持、保持多久，由主 Agent 对照设计决定。

最小合作失败更加直接：`PlanRules` 内 `Ask` 构造的 `Say.Request` 为 `Think(Related(Fx.Target, Promised, door))`（`GameJobs.cs:278–282`）。`Ast.Bind:131–137` 有意保留请求的后续槽位；`WorldRuntime.Deliver:143–153` 映射引用但不填充 `Target`；`DecisionSystem:31–34` 对接收者使用只有 Actor/Scene 的上下文。中性实验得到发送 `Completed`、`Procedure` 存在、社交 `Accept(score=1)`，却没有候选。改用接收者 `Actor` 槽的中性比较立即得到承诺动作 `Completed` 和关系成立。`Seek` 使用已绑定的目标人物引用，不能因此认定所有邀约路径都失败。这个问题属于宿主表达错误，无需新增 Core。

`Staff` 是名单资格的贪心分配，既不检查人物所在位置，也不提交移动、占岗或共同效果（`Council.cs:25–47`）。最小静态反例：A 的信号=4、锁技=3；B 的信号=3、锁技=0；C 的力气=1且健康。A 可解决入口。现算法先选 A 做中继、再选 C 做配重，没有剩余锁技人物而失败；B 中继、C 配重、A 锁芯是可行分配。这只是该函数算法反例，没有创建替代生产分配器。`StationFor` 与 `Staff` 的岗位优先顺序还不同（`GameJobs.cs:136–137`），不能把预审分配当作真实执行分配。

取消与失败方面，宿主用普通 `Set` 占岗并经 `ReleaseStation` 手动清理（`GameLoop.cs:299–317,539–545,939–977`）。Core 实测普通 `Set` 在后阶段失败/取消后仍为1；`TemporarySetUntilEnd` 在同样条件下自动归还为0。因此清理能力已经存在。现有释放函数根据当下 `StationFor(p)` 清理而非记录实际取得的岗位；若资格在占用期间改变，是否清错岗位需要另做针对性验证。

## 3. 广播发布、收听、信任、接受与到场

| 环节 | 所审实现 |
| --- | --- |
| 发布 | `Broadcast` 写 `DemonSaid`，按 `shown` 写 `Feed`，循环全部 `People`。属于直接宿主发布。 |
| 收听 | 每个人立即收到名称固定的纯文本 Testimony Event；没有按位置、睡眠、伤病或感知渠道筛选。若设计明确全域可听，这个选择可以成立，本轮不作剧情判断。 |
| 信任 | 该广播 Event 没有 Subject 发送者、信任权重或源消息标识。不能直接按 `SocialSystem` 证明听者是否信它。 |
| 接受 | 通常纯文本广播没有 `Procedure/Rule/Acceptance`。首日另调用 `Tell(Warning1, Channel.Public)` 写规则接受，是另一条路径；不能把所有广播听闻都视作接受。 |
| 到场 | 晨间 `Socialize` 是时段习惯，课堂/议事到场另走行为或直接位置设置。`TeachClass` 的条件化简为“当前在课堂位置”，不检查广播接受；`Council` 把所有未病者直接搬到会场。 |

源码：`Demon.cs:26–33,47–72,101–123`；`GameJobs.cs:193`；`Rules.cs:235–251,301–353`；`Council.cs:128–132`。因此发布、收到、相信、接受邀约、真实到场这五项没有统一回执链。

其他消息传播并非全无结构：`Social.NewsItem` 有 `Origin/Claim/Day/Slot`，收到消息时保留当次传话者、跳数和来源类别；`Receive` 按对传话者的信任缩放后果（`Social.cs:10–27,212–253`），`HandleTalk` 对部分转述登记 `_transmit` 和事件因果（`Emergence.cs:85–112`）。但是这些宿主元数据与 `Broadcast` 不共用消息封套；所审 `Receive` 没有写父传播事件引用。`KnowsClaim` 命中后主要改来源记载而不重新应用后果，来源与认知更新应分别验证。`Retell` 则主要排队/合并玩家可见转述，不负责客观发布或认知真假（`Retell.cs:4–25`）。

议事助手名单仅由支持者关系和合作值阈值推定（`Council.cs:185–192`），没有逐人正式收到请求、答应、到达和占岗的记录。这是宿主未建立履行链，而非 `SocialSystem` 缺少接受/拒绝计算。

## 4. 通行四层与虚假声明反例

| 层 | 当前状态 |
| --- | --- |
| 实际权限 | `_corridors/_releasedDorms` 与 `HostCanEnter` 是宿主权威集合。 |
| 实际可移动通路 | `RefreshAccess` 清空并重建 `PassageProperty.Connections`；目的地及出发地都须允许。Core Travel 激活时检查实际连接、锁和目标存在。 |
| 声明/发布 | `HostCorridor(name,open)` 同时改变权威集合和追加 `FreeEvent.Corridor`；该事件只有时段、名称、布尔值，没有声明者、声明对象或传播记录。它是权限变更日志，不能当作角色声称通行的证据。 |
| 角色认知 | `RefreshAccess` 将所有路线向全部已初始化人物做 `Rt.Observe`；来源是 Perception，并即时更新各自 `M`。随后主观 Forbid 约束 Travel。没有保留“实际已变但尚未获知”窗口。 |

源码：`Chapter2Access.cs:7–66`；`RoomPresentation.cs:102–110`；`ActionRuntime.cs:220–227`。UI 是否实际显示权限及碰撞通路本轮未验证；公开 `HostCanEnter` 接口不等于已取得 UI 证据。

虚假声明反例 A：正式 Core 的 A 对 B 执行一个声称 Q 可通行的纯 `Say`，发送完成，B 收到带发送者 Subject 的 Testimony；实际 Q 仍锁着，B 的路线标签仍为0。`Say` 本身不验证文本真假，也不自动把文字解释为状态。

反例 B：明确标为“接受证词夹具”的 Observation 把 B 的主观可通行认知设为1。B 经正式 `DecisionSystem` 选择 Travel；正式 `ActionRuntime` 仍返回 `ConditionFailed`，B 留在原房间。这证明主观选择与客观裁决已经分开。夹具认知注入不是正式游戏输入、盲玩或验收。

反例 C（静态接口）：如将“仅声明开放”错误地路由给 `HostCorridor(...,true)`，该函数会立即重建实际连接并向全员写入 Perception；声明将被当作权威权限变更。修正须分清调用语义，不能以 `FreeEvents` 已有记录来证明它已经分清。`SpeechPolicy.NeverLies` 只限制被调用策略产生的 SpeechAct；任意提交的 `Effect.Say` 字符串没有内容证明，实验同时确认这两个边界。

## 5. 对齐 F01 的修正范围与精确新增缺口

已核对 `F01/capability-manifest.json` 与 `source-evidence.json`。F01 的 PARTIAL 常表示作者语法/宿主桥不足，不表示 Core 原语不存在。F01 是只读静态目录，本轮中性实验只为下面列出的公共 Core 组合提供动态证据。

| 可用现有能力完成的独立任务 | F01 对应 | 最小验证 |
| --- | --- | --- |
| 将邀约请求的未绑定 Target 改为明确接收者 Actor 或接收者内部引用；保留拒绝和不可行结果。 | C004、EFF-11/12、C013 | 接受后有候选；拒绝后无履行；请求中的第三者不得被悄悄替换。 |
| 用 `Require(Not Occupied)` 与生命周期租约表达独占，真实移动/到位后取得；取消/失败由租约清理。 | C006、EFF-06/09、ACT-02 | 两人竞争同岗只一人取得，失败与取消均归还实际取得岗位。 |
| 将瞬间共同条件写为 `All(Tagged...)`，条件等待在主观感知更新后恢复，提交时再按实际条件检查；共享效果只提交一次。 | AST-C03/C08、EFF-09/10、C006/C007 | 阶段重叠时成功；无重叠不成功；没有双重共同效果。 |
| 正式请求逐人记录收到/社交态度/实际行动；资格预审与议事支持只作候选，不能直接产生群体完成。 | C013、C010、C017 | 接受但忙碌、迟到、被禁止、临时退出分别留下失败/未履行回执。 |
| 将通行权威变化、声明 Testimony 与各人实际观察分开，沿现有 Projection 和 Travel 裁决。 | C007、C012、ACT-02 | 真实开放未听闻、假开放已相信、已关闭仍记得开放这三种状态分别可表达。 |
| 将上述现有 Core 原语补进受控编译/绑定入口。 | EFF-06/09/10/11 的 PARTIAL | 编译/IR/绑定/执行四层同一结构；不能仅用中性 C# 能执行证明 `.story` 已支持。 |

本轮正向实验以三个演员的租约、现有条件 Wait、All/Tagged、提交时 Require 和同处物件的实际阶段感知组合共享结果：结果=1、三动作全部 `Completed`、占用最终全0。实验没有实现群体事务管理器，没有加载正式章节，没有声称既有 `.story` 入口已经支持该组合。它排除了“要做简单共同条件就必须另建 Core 调度器”的过度结论。

以下是**条件性的公共语义缺口**，不是本轮获准新增项：

1. 若设计要求多人的成功、资源消耗与失败必须整体提交/整体取消，而不只是一次门效果，那么现有 `Submit` 只有单 actor 执行和单阶段事务。需要明确定义参与者/岗位绑定、准备资格、共同提交条件、群体版本、部分到达、退组、超时与幂等清理的群体事务契约；不能由支持人数或资格名单替代。已有普通事务/租约不得再实现一套。
2. 若设计要求三岗连续共同保持一段时间，现有 AST 只有即时条件和定时/条件等待，没有“条件在整个时间区间始终成立”的公共条件或失效回执。起点、终点都检查仍不足以证明中间没有离岗。需要通用持续条件/中断语义，或先以现有正式状态变更事件证明宿主追踪能完整覆盖；本轮瞬间共同条件成功实验不证明持续时间契约。
3. 若需要通用、可审计的广播/传播，则需要公共消息身份、来源主体、原命题/请求引用、接收资格、每次传播父引用、收听回执与独立接受结果。现有 `Say/Observe/SocialSystem` 可实现有限已知接收者，宿主 `NewsItem` 已有部分来源元数据；欠缺的是统一的公共契约和作者通路，而非从零再建信任公式。源链/接收资格也可先整理成通用宿主能力；是否必须进 Core 由架构取舍决定。
4. 若要声明型通路改变，不应把单个角色的真/假发言当成 `PassageProperty` 权威修改。现有 Core 已能表示现实与主观的不同；最小缺口首先是受控通路声明/权威修改和认知输入的作者接口。没有证据要求新增另一套本体模型。

上述缺口只限所审接口；没有声称全仓绝不存在其他可组合设施，也没有根据未读设计批准功能范围。
