# R18 refresh_until 新鲜度提案独立审查

日期：2026-10-15。只审查给定精确提案，依据此前已核对的 departure_goals、证据来源/时间比较、c2d_refresh_actor_goals 和主体认知更新合同。未修改源码、运行会话或构建，未读取设计与私有轨迹。

## 结论

该提案作为显式声明的持续复查动机，有条件可接受：只读本人认知，修改目标的新鲜度要求，不直接授予 solved 真值、不新增频道、不指定行动。它比无条件刷新所有目标更窄，也保留真实 inspect/Complete 的获取边界。

但它不能单凭源码保证旧 false 一定更新：actor.mind.time 若仍停在旧观察时刻，刷新到同一值仍被旧观察满足。这不是提案引入的知识漏洞，却是必须保留的有效性限制。应在新会话实际记录时间界限、本人观察时刻与选择，不能把 helper 被调用当作重新检视已经发生。

## 公平性与认识边界

- refresh_until 由四个原生目标显式声明，其他 goal 不参与；条件只读 actor.mind，不偷看 physical 或其他人的完成状态。
- 条件非真时要求当前本人已知时刻的新证据，表示本人尚需复查，不表示事实已经改变或完成。既有观察、已知值、来源与接收记录均不能被改写。
- 不得为让刷新立即生效而给 mind.time 写入全局时钟、用当前真实 solved 决定刷新、或人为把 minimum_time 设成未来值。
- 完成条件由本人真实认知达到 true 后停止刷新，保留既有获取路线；不应顺带把 global completion 当成已知。
- 这仍是动机/新鲜度规则变化，应另立来源指纹，不称同条件提速。

## 新鲜度和重复劳动风险

现有满足检查允许 observation.time == minimum_time，因此同一认知时刻的成功复查会满足要求，理论上不会仅由 helper 在相同时刻反复要求再查。后续本人获得更新时刻，未完成条件仍非真时，目标会再次需要新证据。

四项目标都用总体 c1dep_complete 作 refresh_until，意味着哪怕其中一项已知不可逆为 true，只要其他项未完成，该 true 项也会随着时间被重新要求刷新。这比“只复查尚未完成的单项”更宽，可能增加一次检视的信息分；当前同一个 inspect 同时读取四项，故不必然增加四次实际行动，但会影响价值比较。若保留总体条件，应明确这是提案有意要求的整组复核，而非宣称每项已完成事实立即免刷新；若目标是不复核已知不可逆单项，需改用各自的条件。不能在实现时静默替换语义。

已知时刻变化不是完成状态变化的证据，因此该策略可能产生合理范围内的轮询，也可能增加重复检视。需以实际行动、原始输入与资源消耗判断，不保证消除停滞。

## 预算与别名

规则不增加额度，但额外检查仍消耗原动作、规划、认知等资源。不得通过本 helper 清理 used/attempts、重置预算或跳过正式前提。

实现应新建 goals 结果容器；只对符合条件的 goal 使用原持久更新方法返回新 goal，不能原地修改 cached departure_goals、policy、旧证据或历史初始快照。不匹配的目标顺序和值完整保留。刷新只改变 minimum_time，保留 ref、source、basis、scope、available_when 和 refresh_until；不得丢弃来源限制。

## 后续最低核对

exact diff 应仅改变原生四个目标的 metadata、通用刷新 helper 及指定组合调用。新会话须记录：本人当前 mind.time、旧 solved 观察时刻/来源、刷新后的界限、实际复查、获得的新值，以及之后真实释放/跨门。若 mind.time 未前进或预算先耗尽，应如实记为未解决，不用强制行动补证。
