# 4 倍速卡顿实测与修复

分支：`codex/shared-ai-learning-20261011`。使用正式渲染 FullTest，seed=0、time-scale=4、max-seconds=180、line-seconds=0.6、shot-seconds=10。未注入游戏状态或正确路线。

## 两个已定位原因

1. **持续卡顿：NPC 每个物理步重复绑定相同策略，并重跑完整推理。** 4倍速采用240Hz物理步。旧 `StrategyPolicy.Bind` 每次都写入内省观察，即便规则完全相同；认知历史持续增长，`ActionLearning.Assess` 的 `SnapshotGraph.Build` 成本也随之增长。r18后段20秒主线程采样中，`TryStrategyAction` 包含约19.065秒，`SnapshotGraph.Build` 包含约15.807秒。它们是嵌套采样耗时，不可相加，也不是精确CPU百分比。证据：`verification/performance-r18/sampled-stacks.json`。
2. **首次展开霍铎菜单的停顿：同步冷初始化。** 菜单条件进入 `Credence → SyncConception → AwakeningCase.Model → Build → NightReplay.Run`，第一次生成全部组合的案件模型。独立冷启动采样记录此链约6.61秒，r19单次选择调度6.055秒。证据：`verification/performance-r19/cold-sampled-stacks.json`。并非对白等待，也不是单次玩家决策耗时。

## 已实施

- 相同规则、条件、权重、时效和说明的策略绑定不重复产生内省记录。
- NPC派生评分只在同一主体同一认知版本复用；认知与行动反馈变化后失效，不修改角色能力或规则。
- 宿主就绪时后台准备原有只读案件模型；每个预测使用独立重演世界，不碰活会话或Godot对象，不提前给人物答案。同步入口仍保留，若读取早于准备完成仍可能等待。
- 记录实际过程帧率、窗口P95/最长帧、世界调度/决策/观察刷新耗时、实际绘制等待、阅读等待与同步截图耗时。

## 实测结果与限制

[折线图](verification/performance-chart/performance.png)、[帧数据](verification/performance-chart/frames.csv)、[等待与观察数据](verification/performance-chart/timings.csv)。图只保留第一章，r20在150.226秒出现终局后截断，不能把后章高帧率混入第一章改善。

- r18全程最长帧5,671.968ms；r20第一章最长帧1,001.894ms。**仍有卡顿，未达到持续流畅。**
- 首次菜单附近，r18选择调度最长5,622.535ms；r20对应窗口最长5.300ms，冷初始化尖峰消失。
- 等待实际绘制：r18 P95为1,069.2ms、最长1,987ms；r20第一章P95为144.4ms、最长351ms。
- r20仍有4FPS左右的一秒窗口；后续世界更新和坐席决策仍有数百毫秒峰值。同步截图也是额外开销，已单独记时。
- 自主轨迹会因真实时序变化而分岔，不能把不同状态的均值当成严格同状态性能比。r18中段还包含约20秒采样剖析，可能增加测量负担；严重慢帧在剖析前后都出现。

工程检查与原始失败日志分开保存在 `verification/performance-r18`、`performance-r19`、`performance-r20`。所有原始轨迹/截图/运行日志及采样文件保留在本任务 `runs/`，SHA256清单随报告保存。独立工程检查不能证明人物行为或体验合格。
