# C# 模拟引擎架构与外部接入规范

本次以 **C# 为实现主线**，依据 2026-09-05 的代码和 `five_days_trajectory.md` 选择性审查。Python 是参考实现，尚未同步本轮会话接口。本文规定当前新游戏接入方式；跨语言替换仍须另行通过相同场景验收。

后续修正方向已在[低配置涌现核心改进方案](./emergence-core-plan-zh.md)敲定。该方案以规则、契约与言灵的共用后果机制为中心，优先级取代本文第 6 节的初步排序；本文仍记录当前已经实现的接口。

最新设计以[文学范式与人物模拟设计](./literary-simulation-design-zh.md)为准：Core 将默认提供灵异物品、数值和人物交流，旧接口无需兼容。本文描述的现有接口不构成后续兼容承诺。

## 1. 能力判断与依据

修改前已有离散模拟原型：实体拓扑、有限物资、主观规则、客观契约、效用选择和嵌套反应都有实际代码。它能运行学园游戏，不能据此认定已经具备通用、低配置的模拟架构。

历史轨迹抽读了第一日开局、第五日末段，并对照生成代码：

- 第 8 步饮水消耗份数；对应进食闭包实际扣除 `Servings`。有限物资具有真实状态，不能将全部轨迹归为纯文案。
- 第 525 步前后多人饱腹为零仍正常工作。需求数值尚未充分连接身体后果与资源求生计划，长时间饥饿可以只改变评分。
- 第 529 步仍在检修设施。原候选未排除 `MaintenanceDone`，执行主要设置完成标签并发放情绪收益；缺少磨损、工具与材料闭环。
- 动力旁路、结界破解等行动通过特定名称和世界标签串联。此类谜题可以留在游戏层，不能作为通用设施网络的证明。
- 原 `AcademySimulation` 使用额外角色优先队列；`SimsMotiveProfile.Decay` 按所选行动代价消耗，夜间另扣 80 AV。时间推进与状态演化分散在宿主流程中。
- 原核心虽无 Godot API 引用，独立 runner 仍引用 Godot 工程。更换游戏需要携带不必要的构建依赖。

以用户给出的游戏为设计参照，本项目追求的是属性与资源的组合后果、需求驱动选择、社会认知传播，以及装备和生产的持续约束。这是本项目的目标提炼，不是对这些商业游戏内部实现的复刻声明。房间内空间、碰撞、实时运行和 UI 仍由游戏层承担。

## 2. 已敲定的依赖结构

```text
Godot / 控制台 / 其他宿主
            ↓
游戏内容与世界构造（学园、资源村、未来游戏）
            ↓
Core.Simulation：SimulationSession、Affordances
            ↓
ActionRuntime、Timeline、Soul、Rule、Kotodama
            ↓
Entity / TreeMember / Facet、场景拓扑
```

`core/DualOntologyWorldEngine.Core.csproj` 是独立 .NET 8 库，不引用学园或 Godot。`simulation/DualOntologyWorldEngine.Simulation.csproj` 是学园游戏内容库。目录名 `simulation` 为历史命名，不表示其中所有机制都属于通用核心。Godot 根工程引用二者并编译表现层。独立资源村仅引用 Core。

核心负责状态载体和执行语义，不内置职业名、食物枚举、章节、固定昼夜长度或全局人类需求表。可复用机制以普通函数及已有 Facet 挂载；当多个游戏确有相同逻辑时再抽取独立机制库。不要为每种物品增加数据类、对象定位 ID 或另一种配置语言。

## 3. 外部使用框架

一个新游戏只需完成以下接入：

1. 建立 `Entity` 世界、场景、对象与绑定了 `Soul` 的 `Character`。
2. 通过 `target.Offer(factory)` 发布对象提供的行动。工厂返回已有 `Intent`，可供任意角色复用。
3. 用 `soul.Discover(perceived)` 接入感知范围查询。默认不扫描全世界；藏匿、门禁、知识限制由该查询及行动条件表达。
4. 创建 `SimulationSession(world)`，通过 `Activate` 安装角色效用与选择器，以 `Timeline.Step/RunUntil` 驱动世界。

既有 `Soul.InstallStep`、偏好、承诺和规则继续适用。`Offer` 表达对象提供的机会，Step 表达角色特有能力或计划候选，两者进入同一个排序与复核管线。

| 接口 | 契约 |
| --- | --- |
| `Activate(actor, soul, ...)` | 同一身体只保留一个自主槽；替换不会清除剩余行动代价。无候选按 `idleCost` 重试。 |
| `Deactivate(actor)` | 取消自主槽。已发生的动作、反应成本和外部命令继续保留。 |
| `Submit(intent, completed)` | 排入外部命令，返回取消函数；等该身体恢复后再次审查，不保证提交时的候选仍有效。 |
| `ReadyAt(actor)` | 查询下一次普通行动最早时间。 |
| `Runtime.Review(intent)` | 客观可执行性检查；主观规范只参与决策压力。 |
| `Runtime.BeforeReactions` | 主效果之前的拦截机会，反应后重新审查主意图。 |
| `Runtime.ReactionHandler` | 观察已发生 Event 后的反应，不能撤销已经结算的主效果。 |
| `Timeline.Advanced` | 实际 AV 增量通知，用于需求、衰减等连续过程。 |
| `Timeline.Schedule` | 世界过程或计划节点的离散时点；只能使用这一条队列。 |

玩家可通过 `Activate` 的 chooser 选择当前候选。异步 UI 则先 `Deactivate` 接管，再提交 `Submit`；恢复自主行为时重新 `Activate`。UI 不直接执行 `Intent.Execute` 或修改世界资源。

同一 Runtime 由一个 Session 管理。`ResolveDetailed` 是即时结算的底层接口，不等待身体恢复；普通玩家与 NPC 应使用 Session，只有嵌套反应和机制验证直接进入 Runtime。Session 释放时撤销自己登记的角色槽及命令；游戏自行解除其注册的过程和监听器。

## 4. 时间、反应与结算规范

采用“行动槽即时生效、行动值延后下一槽”的离散语义。MotionCost 必须为有限正数。时间线可以用零延迟登记同刻的一次性任务，周期任务必须让 AV 前进。

嵌套反应在当前时刻递归结算，不推进另一个时钟。每个实际执行的反应将成本累加到其身体的恢复时间：`readyAt = max(now, readyAt) + motionCost`。这是回合制反应债务，不表示两个普通动作同时执行。需要限制反应次数或禁止疲劳反应的游戏应在反应提供器中表达条件。递归上限默认 16。

完整管线为：候选发现 → 客观筛选与主观评分 → 选定 → 客观复核 → 前置反应 → 再复核 → 执行并记账 → Event → 成功时的契约与心智后效 → 见证 Observation → 事后反应 → 监听器。

前置反应的 `cause` 引用待执行 Intent；该主意图可能被阻止，因此不能伪造其成功 Event。事后反应的 `cause` 引用已经发生的 Event。见证者去重，观察只宣告事件发生，不自动断言其效果成功。失败必须检查事件的 `succeeded`。

拒绝执行时不产生成功事件、不扣行动代价，自主槽按空闲代价再试。闭包实际执行后返回失败仍保留失败 Event 并支付成本。`EffectResult(false, ..., reason)` 表达预期失败；异常属于机制实现错误，不吞掉，也不声称自动回滚。

`RunUntil` 达到步数预算时保留实际进度。调用者检查 `Now` 后继续推进，不能假定返回即到达目标时刻。

连续过程按 AV 增量计算，不能按每次动作扣减同一段时间。过程应保持分段一致性：推进 10 AV 与推进两段 5 AV 得到相同结果。需要精确触发伤害、腐烂、开门或供货阈值时，应显式登记离散任务；不能在大步推进结束后补写发生在过去的事件。`Advanced` 回调不递归推进 Timeline。

## 5. 机制编写与状态规范

- 候选工厂、效用计算、`Validate` 只读取状态。执行前再次检查资源、对象位置、工具、访问权限以及尚未完成的目标。
- 扣除投入和产生结果属于同一个行动闭包。资源满足与心理满足分开，烹饪产出食物不等于角色已经进食。
- 同一事实只有一个权威状态源。关系使用对象引用；派生描述与日志从状态和 Event 读取。公开文案不能替代实际状态变化。
- 完成标记必须参与后续候选条件；要重复生产或维护，先有实际消耗或磨损过程使条件重新成立。
- 随机性属于游戏实例，显式持有种子和 RNG。保证可复现还要求对象注册顺序、候选顺序与随机调用顺序一致。
- 监听器需要直接改变另一主体行为时，应形成具备来源的偏好、认知或新 Intent。涉及独立资源消耗的行动仍通过 Runtime 执行。

当前没有通用多对象事务、存档协议和自动状态差分采集。不要把任意闭包视为自动满足资源守恒；正确性仍取决于机制代码。没有实际需求时不增加统一资源表或序列化 ID。

## 6. 本轮改动与仍缺少的能力

本轮完成独立构建边界、对象行动机会接入、统一 Session、外部命令、前置拦截、反应成本、时间增量、观察传播与学园调度迁移。修正时间预算跳跃、重复激活、进食重复奖励、烹饪无消耗饱腹奖励、维护完成后仍反复获益，以及进食缺少执行前资源复核的问题。

目前适合建立可测试的小型离散模拟沙盒。尚不能宣称达到完整生活模拟或系统化角色扮演游戏的机制深度。后续主要缺口按优先级是：

1. **跨机制持续后果。** 学园的饥饿、污染、设备状态尚未全面接入身体损伤、材料转化、磨损与生产流。应先做一个完整可复用机制闭环，再扩充职业文案。
2. **可中断的多步计划。** 当前有承诺惯性与候选选择，缺少通用的“找原料—获取工具—移动—生产”计划及资源被抢占后的重规划。不要用职业名分支代替依赖关系。
3. **社会认知的覆盖。** 底层已有观察、信念、关系和规则传播，但学园部分候选仍直接读取全局剧情状态，尚未全面受角色知识和信息来源约束。
4. **长时间运行与存档。** Event、Observation 和 Decision 持续累积；尚无保留策略、存档恢复与大世界性能验收。

学园夜间仍是内容层批量作息，含回宿舍与恢复的直接状态操作。此次迁移统一了时钟与需求消耗，没有将全部夜间行为改成拓扑移动和床位竞争。旧剧情动作仍逐项保留，尚未全部迁入对象 Offer。两者是明确的后续迁移范围。

## 7. 可执行验收

```powershell
dotnet run --project godot_csharp/tests/runner/runner.csproj -- --verify
dotnet run --project godot_csharp/examples/resource_village/DualOntologyWorldEngine.ResourceVillage.csproj
dotnet build godot_csharp/DualOntologyWorldEngine.csproj
```

`--verify` 包含既有核心机制与食物闭环检查、新的时序和拦截验证，以及不导出文件的学园五日运行。独立资源村仅引用 Core，以实际有限资源验证同初态可复现、改变供应改变选择和资源不透支。它是最小反事实验证，不是对大规模涌现能力的充分证明。

历史 `docs/five_days_trajectory.md` 保留原样。其具体动作顺序不再代表修改后的运行结果；运行旧 `--auto` 仍会导出轨迹，日常验证优先使用 `--verify`。
