# 32 技术路线

## R3正式空间设计与实现状态（2026-10-31）

现行空间入口为 [12 房间布局](12%20房间布局.md)。四院、双侧分级房、R13平开B/S、S/M/T、名录库与高位出口按新图迁移；不实施被否决的R2四电梯及统一病房。绘图JSON/CSV只是作者数据，不能成为世界规则或人物认知的第二份运行实现。

所有具体房间、门窗、家具、气路、人路、货路、源质与认知初值由DV声明；C#提供通用机制。动作经过准备、真实执行和完成回执后才提交位置或状态。旋转舱正常/救援/损坏、B/S/W1、折桌、长梯、浮钟与独立桥卷扬分别建模。

本轮完成设计与尺寸审核，没有运行R3游戏。真实DSM不等于裸地测绘，正压和旋转舱不保证零污染，浮钟数字不证明桥梁承载。发布前分别完成CLI/Godot与自动/AI测试，保存真实回执；旧存档保留版本或有记录转换。


## Core、DV与宿主职责

DV 声明剧情、人物倾向、认知初值、规则、物体、房间拓扑和世界法则。C# 实现解析、条件求值、效果应用、证据更新、主观推理和行动调度。CLI 与 Godot 共享会话语义，各自负责输入和显示。构建直接编译维护的 C#，运行时解析并校验完整 DV 内容包。

## 世界事实与人物认知

游戏以本地 C# 演算和 DV 内容支持十六名学员的群体博弈。客观层记录位置、门锁、物资和事件。各人物持有独立的观察、来源、时间、信任和冲突状态。认知盲区与遗忘条件由 DV 声明，Core 执行感知过滤、记忆更新和推理。

过滤作用于对应人物的观察，物体仍保留在客观世界。

保存真实声源、感知结果和实际动作的独立记录。

记录人物何时遗忘、何时重新观察。证言可以来自真诚信念。

## 事件装配与时间推进

DV 声明事件前提、参与资格、证据、行动和结果，Core 按当前状态匹配角色。渴望值 `W_drive`、谨慎度 `S_caution`、信任关系和压力变化是候选匹配参数。

呈现帧、环境推进、人物决策和昼夜结算按职责更新，具体频率和扩散参数由实际实现记录。房间拓扑、门窗、高差、源质来源和浓度参与环境演算。模型需维护边界、非负浓度和来源守恒等所选规则。

## 保护判断与实体调度

人物通过观察、交谈和证据形成认知，并保留来源和冲突。知情索引用于快速筛选，完整判断使用对应人物对具体危险的认知。身份和成员资格由 DV 声明。恶魔保护动作由条件、动作资源、可达性、优先级和完成状态共同决定。

门闩、脱扣杆和逃生路径作为世界物体与规则进入演算。Godot 呈现对应几何并执行运动。任何穿透或位置转换都需要正式行动授权及回执。环境变化后的可达性须与 Core 状态一致。

保护资格来自 DV 的 `protected` 身份声明。Core 根据实际登记成员和危险范围计算需要检查的人物，再检查对具体危险的认知。资源占用、移动、动作完成和保护优先级单独演算。错误信念、争议与信念强度保留在人物认知中。

代管者的单一物理实体使用资源标识 `DemonEntityLock`。写字、开锁、搬运和拦截等施力动作占用该实体；实际可达动作、耗时与资源占用由正式演算决定。

多人同时遇险的处理顺序和规则冲突需要补充。相关剧情方案须记录保护动作的完整前提。

## 呈现层实现

### 地图画面系统设计（2026-11-01，设计目标）

本节规定地图画面与人物画面拆分后的地图职责和迁移顺序。以下接口与文件拆分是设计目标，尚未按该合同完成改造，也没有新增游戏运行或通关验收结论。

#### 同一现场的三维装配

同一可见现场内，地图节点和人物节点是同一三维世界中的平级组件。Main 装配共享渲染上下文，交付同一 `World3D`、米制坐标系、相机和全局 `Environment`。地图系统不再通过另一套相机或 `SubViewport` 渲染后叠加人物画面。地图局部灯具、建筑遮光体与反射捕获体仍由地图组件持有，并共同影响建筑、家具和人物。

这个边界按现场生效，不要求全进程只有一个 `World3D`。现有 `DvFieldExecutor` 为不同地图保留的 `execution_only` 物理上下文可以继续隔离。非画面上下文的碰撞、路线和执行结果不能冒充当前可见现场的实机画面。

Main 是正式会话投影的唯一分发者。`Session.Project(viewer)` 具有消费游标，Main/GameEngine 每批只消费一次 `HostStateDelta`，再把同一只读帧分发给地图系统和人物系统。两系统不能分别拉取或推进会话。帧沿用 `content_hash` 和 `state_version`；生命周期用 `session_generation`、`map_id`、`map_generation` 标识。`map_generation` 只表示现场节点或空间发布替换，不代替 Core 世界状态版本。导航另用 `navigation_revision` 标记路径数据变化。

DV 设计坐标保持米制，X 向东、Y 向北、Z 向上；进入 Godot 后统一经 `DesignCoordinates` 转为 X 向东、Y 向上、Z 向南。建筑基准点、楼层标高、房间范围、门洞与交互锚点都来自同一发布。两个画面系统不能各自猜测原点、固定增补楼层高度，或把旧像素坐标当作三维位置。保留的旧输入适配只做协议坐标转换。

#### 地图系统的文件职责

| 文件或目录 | 设计职责 | 不承担的职责 |
|---|---|---|
| `scenes/architecture/ArchitectureController.gd` | 地图组件入口；管理空间加载、版本、资源保留、投影分发和地图端口 | 不持有人物模型、角色动画、玩家相机或可修改的 Core |
| `scenes/architecture/BuildingFramework.gd` 与墙、地板、门窗、楼梯构造模块 | 从已发布 DV 装配建筑、家具、局部灯具及物理形状；各对象保留稳定 ID | 不从人物名字或剧情状态重建第二份布局与规则 |
| `scenes/architecture/MapSpaceIndex3D.gd`，拟新增 | 统一索引房间、楼层、门洞、地面、支撑面和导航发布；提供只读空间查询 | 不驱动人物，不判断人物的钥匙、权限或所知 |
| `scenes/architecture/MapObjectRegistry3D.gd`，拟新增 | 注册门窗、家具、容器及其交互锚点；提供按 ID 查询与物体运动端口 | 不靠遍历任意子树猜对象，不提交物品归属、门锁或剧情结果 |
| `scenes/architecture/MapVisibility3D.gd`，拟新增 | 消费观察者可见性帧，分发房间黑雾、记忆显示、门窗切片和近墙裁切参数 | 不直接读取全知状态增加人物知识，不驱动人物显隐之外的动作 |
| `scenes/rendering/` | 继续维护共用表面 Shader、裁切 Shader、遮光与渲染参数 | 不复制建筑声明，也不为地图和人物建立互不相容的光照标准 |
| `scenes/Main.gd` 与宿主组件 | 装配共享上下文、分发会话帧、协调人物与物体执行、接收回执 | 不把具体房间、门或案件规则改写为宿主分支 |

`MapSpaceIndex3D`、`MapObjectRegistry3D`、`MapVisibility3D` 是候选拆分文件名。实现时先保持正式入口和现有资源路径，再逐项迁出职责，避免一次替换成无法游玩的第二个宿主。

#### 对地图和人物公开的端口

公开结果是带版本的只读值或有效期受控的句柄。`rooms`、`_dv_buildings`、可修改材质、对象节点字典及导航 RID 的管理权不交给人物系统。查询可借用碰撞 RID 识别接触对象，但接收者不得修改或释放该 RID。

| 端口 | 输入与输出要点 |
|---|---|
| `ensure_space(request)` → `space_ready` | 请求包含生命周期标识与所需房间、通道、交互对象；返回资源、物理形状、导航同步分别就绪的状态及错误。构造函数返回不等于物理帧与画面已经就绪 |
| `retain_space(request)` / `release_space(handle)` | 为可见范围、人物身体、在途路线或交互阶段保留所需资源；句柄绑定生命周期，释放只解除该持有者的保留 |
| `resolve_room(world_position)` | 返回房间 ID、楼层 ID、标高与所在门槛区域；门洞厚墙区保留已发布的相邻区域归属 |
| `resolve_ground(query)` | 返回实际地面或支撑面位置、法线、表面 ID、有效范围与版本；射线未命中或支撑尚未就绪时明确失败 |
| `resolve_target(target_id, slot_id, context)` | 上下文携带现场生命周期和所需版本；返回稳定对象 ID、锚点 ID、世界变换、接近位、站位、朝向、接触容差及 `target_revision`；同时返回目标的只读碰撞 RID 集合或 `collision_owner_id`，供人物判断接触到的是目标还是附近墙体 |
| `query_route(query)` | 返回世界坐标路径、经过的门洞、所需地图保留句柄及 `navigation_revision`；明确所用实现是现有房间图路径还是已同步的三维导航网格 |
| `query_clearance(query)` | 返回门洞、门槛、支撑面或动态家具的客观净空、阻挡物及当前版本；不把物理可通行直接当作人物已经获准通行 |
| `apply_world_projection(frame)` | 接收宿主交付的 physical/executor 投影，更新真实门窗、灯具、家具和物理执行所需状态；不把这些字段自动显示为玩家知识 |
| `apply_visibility_projection(frame)` | 接收 observer 可见、可读和最后所见投影，更新地图画面；与人物系统消费同一批最终显隐条件 |
| `execute_object_motion(intent)` → `object_motion_result` | 仅执行宿主已准备的门窗、抽屉、机关或动态家具运动，测量扫掠、净空、接触和阻挡；结果经 Main 汇总后送入正式完成回执，不自行提交 Core |

全部结果回带 `session_generation`、`map_id`、`map_generation`、`content_hash` 和适用的 `state_version`。`target_revision` 只在目标锚点或碰撞几何变化时更新；`navigation_revision` 在相关连通性或障碍变化时更新。Main 与人物系统在执行阶段交界处复核所需版本。旧生命周期的异步加载结果、运动结果和句柄必须失效，不能被接到新局或替换后的地图上。

#### 静态构件与动态物体

静态墙、楼板、固定家具和楼梯从同一发布生成视觉、碰撞和导航输入。可复用网格、材质和静态批次可以共享；对象身份、锚点、容器状态、灯光开关、动态运动及占用记录保持实例独立。参与交互或运动的家具不能只存在于无法单独定位的合批网格中。

门窗、抽屉、折桌和机关的机械运动归地图组件。人物系统负责身体到达、朝向、手脚与物体接触及角色动画。Main 协调双方的动作阶段，并汇总同一正式行动的测量结果。地图系统不能因为门扇达到目标角度就判定人物已经穿门，也不能因为手靠近把手就改变门锁或消耗钥匙。

人物动画与物体运动按 DV 声明的接触阶段和时间点同步或依次执行。宿主核对双方的同一行动标识、阶段和真实结果，再提交完成；不能统一等人物动画结束后才启动所有物体运动。拿放物品由 Main 依据 Core 接纳结果协调地图实例与人物手部插槽的所有权转移，两个系统不得同时生成同一物品的独立实体。

运动期间检测真实扫掠区和门槛占用。失败、取消或状态版本改变时返回真实阻挡与当前机械位置；不能强制穿过人物、直接瞬移复位或伪报成功。后续恢复动作仍须经过宿主协调。人物实际运动与临时占用经 Main 传入地图端口，地图不得自行写入 Core 的座位预约或世界位置。

#### 房间加载、裁切和黑雾

加载至少区分视觉资源、碰撞与导航数据、交互锚点三个部分。当前可见房间、视线允许的门窗切片和即将经过的走廊可保留视觉；在途人物或交互保留的空间继续保有碰撞、导航和锚点。隐藏画面不销毁远处 NPC 仍需使用的物理上下文，也不使其停止 Core 调度。

同一层多个房间共用建筑根节点时，不能把隐藏该根节点当作卸载单间房。实现先建立房间与批次、动态对象、共用结构的索引，再按实际持有者释放资源。共享墙体、跨房间地板和楼梯按关联区域合并保留，避免临界处突然消失或丢失碰撞。

地图产生几何遮挡与门窗切片的候选结果；Main 将其与 observer 投影协调后，向地图和人物分发同一可见性帧。当前可见房间按实际光照显示，未知区域保持隐藏或纯黑。若显示已探索房间的暗化记忆，只能使用该人物最后所见的静态状态；离屏人物、门锁变化和实时机关运动不能通过记忆画面泄露。名称、标签、轮廓、阴影和局部灯光同样遵守可见性限制。

近端墙体裁切只改变观察显示，不删除墙体碰撞或通行约束。地图与人物使用同一相机变换、米制裁切阈值和房间可见性参数。`observer_position_world`、`eye_world` 与 `floor_elevation_m` 分别传递，不再依赖含义不清的单个 `eye` 参数推算全部标高。

#### 碰撞和导航发布

地图发布客观空间与机械净空，人物执行器负责身体运动、避让和实际到达。Core 保存人物依据所知规划的路线及行动许可。两者的结果分别记录，地图不能用全知的物理状态替代人物认知，也不能用 Core 计划路线跳过宿主碰撞。

迁移保留现有房间连接图与房内碰撞路径的明确实现标识。已有 `NavigationLink3D` 节点不代表全图已经改用 `NavigationRegion3D`。后续三维导航发布必须覆盖静态可走面、门洞断口、楼梯连续面及跨层连接，并经过物理和导航帧同步后才进入 ready 状态。

关门不能只关闭局部避让。门洞两侧路径区域保留受控断口，仅在客观状态与真实净空允许时启用对应通行 link；关闭 link 后不能被区域边缘自动连接绕过。门扇和动态家具改变碰撞或路线后增加相关导航版本，宿主使受影响路径重新查询。地图返回的失败原因须区分未加载、版本失效、拓扑不连、门洞净空不足、目标未发布和实际动态阻挡。

#### 当前源码缺口与迁移顺序

当前 `Main._assemble_stage` 将 `ArchitectureController.rooms` 与 `_dv_buildings` 直接交给 `CharacterStage3D`。人物组件还遍历建筑注册交互对象、计算空间路径、切换相机环境并更新地图观察。当前地图加载隐藏的是整层共享根，房间级释放尚未形成独立资源边界。`BuildingFramework` 中仍有依据物体 ID 推断家具种类和适配器固定基准点的兼容路径。`ArchitectureController` 已创建门洞 link，但正式人物路径仍包含房间图与房内栅格逻辑。上述内容是源码现状，不是本设计已完成的功能。

迁移按以下顺序实施，每步均保留 `scenes/Main.tscn`：

1. Main 建立共享渲染上下文和只读帧分发，固定生命周期、米制坐标与物理投影/观察投影的边界。两系统先共用现有正式世界，不切换剧情或地图内容。
2. 地图入口建立空间索引和对象注册，补齐稳定 ID、目标锚点、碰撞归属与资源保留句柄。人物系统改为查询端口，撤销直接持有可修改地图字典及遍历建筑子树。
3. 将相机和全局环境从人物组件移到共享上下文，将地图观察、局部灯具与机械物体运动收回地图组件。双方只接收同一宿主帧和已准备意图。
4. 建立房间资源索引和统一可见性帧，分别验证门窗切片、墙体裁切、未知黑雾、静态记忆与人物遮挡。先证明视觉隐藏不会破坏仍在执行的碰撞与路线，再做资源卸载优化。
5. 迁移或发布三维导航网格，并单独验证门洞状态、楼梯标高、相向占用和多房间连续运动。现有房间图路径在切换前继续标记实际实现，不能把新建节点数量当作验收。
6. 通过正式新局的人工/Agent 输入和两宿主引擎自动测试，记录实际可达范围、真实运动回执及场景图片。模型预览、地图总览和静态检查不能替代角色到达、物体接触或章节完成。

### 案卷绘制与显示

证物绘制使用预制轮廓与笔顺遮罩，SDF可辅助边缘处理；笔顺由路径或时序数据提供。

### 音频实现方案

首版可使用预处理音频保证各站点的叙事内容，再用音频总线处理环境效果。需要动态门限时，另行实现并验证相应 DSP。

日常曲慢放的实现需要比较变速降调、实时保调和独立慢版，试听后确定采用方案。

# Godot 外部时钟的当前范围

## 已实现

Godot 会话采用单调时钟。每次动作完成回执携带从上一次回执到本次回执的实际秒数。Core 将秒数除以 60 后推进世界分钟，并按环境边界依次演算。第一次计时从第一个动作的宿主执行开始。两次回执之间的阅读、空闲和计算时间在下一次回执时提交。世界在没有后续回执时不会主动提交这段时间。

动作在当前已提交的世界时刻准备，Godot 完成后检查当时客观前置条件并提交。原始人物认知仍在准备边界保存。DV 声明的动作成本和其允许范围继续用于账本，实测耗时单独记录。预计到期时间与宿主执行开始时刻分别保存。CLI 继续使用原有声明时长排程。跨宿主读档时转换已排队动作的到期字段。

宿主动作串行。一个动作等待 Godot 完成期间不执行其他人物；完成后其他人物从更新后的同一世界时刻继续。NPC 等待保留在 Core 排队，并在共享世界时钟达到到期或满足中断条件后派发，派发后不再次等待完整时长。环境演算不使人物自动知道客观变化。离屏移动仍可使用房间图近似，跨房间重定位不计入真实物理距离。

玩家等待在 Godot 等待声明的分钟数对应的实际秒数。可中断等待提供 ui_cancel 输入，并按实测时间提交取消回执；该路径尚未完成实机验证。等待期间不运行其他人物，也尚未接入环境事件实时中断。

惰性提交期间的准备和选择事件使用上一次已提交的世界时间。它们还不是经过空闲时间校正后的真实开始时间。需在准备前引入宿主时钟同步，并处理环境变化对准备和认知的影响，才能消除这一差距。

## 视角遮罩、游戏时钟、移动耗时与门导航规范（2026-11-01）

### 一、 受限俯视角与房间级黑雾裁剪

#### 设计目标

场内默认采用固定倾角俯视角。当前所在房间正常照明并渲染，房间外部与未探索/不可直视区域渲染为纯黑遮罩。敞开的门洞与受控窗洞仅按视线几何显露有限切片，朝向相机一侧的近端墙体执行半高切墙或遮挡渐隐。黑雾区域内的 NPC 继续在 Core 中更新逻辑位置，不在黑雾中直接显示三维网格，防止跨墙透视破坏双本体认识论证据边界。

#### 实现状态

当前已接入 `scenes/rendering/CameraOcclusion.gd` 与 `scenes/rendering/CutawayLighting.gd`。正式 `scenes/Main.tscn` 下整栋 R3 建筑的房间级纯黑遮罩、门窗视锥切片裁剪与近端切墙尚未完成实机验收。

### 二、 游戏时钟：单调外部时钟与情境分流设计

#### 已实现状态（来自 runtime-clock-and-door-navigation-20261101.md）

正式入口是 `scenes/Main.tscn`。`WorldStage3D` 与 `LegacyDvMap` 读取 `assets/data/95-configurable-building.data.dv`，发布版本为 `R3-hall-flush-rear-wall`。四隅角堡已经接入，不需要再次发布或以候选场景覆盖正式资源。完整地图、机关及所有 NPC 通路尚未验收。

Godot 保持现实一秒对应游戏一秒。动作等待由宿主执行，完成回执才提交动作结果。新增空闲时的单调时钟提交（`simulation_pulse`），使用 Core 的环境边界推进世界；会话统一维护时间游标，避免空闲推进与下一次动作回执重复计时。HUD 显示时分秒，并在两个正式快照之间插值。插值不提交动作或新增人物知识。当前实现中阅读和查看书页期间世界继续流动。CLI 继续使用形式行动时长。

动作执行期间仍采用串行执行，环境时间在完成回执处提交。当前不是全体人物同时进行物理动作的实现。HUD 秒钟流动不能作为并发世界模拟已经完成的依据。

时钟快照使用独立事件（`clock_state`），不关闭玩家选项或打断阅读。每次空闲提交后旧预计算令牌失效。存档恢复重新建立本次宿主的单调时钟，不累计关闭游戏期间的现实时间。

#### 情境分流时钟设计目标（待进一步收敛）

为兼顾从容推理与世界实时感，后续时钟策略按玩家状态分流：

1. **阅读与推理态**（打开案卷 `Casebook`、查看证物细节、进行自然演绎/逻辑推演、浏览模态选项）：目标为暂停世界逻辑时钟推进（$\Delta t = 0$），避免玩家在整理证据链或阅读长文本时错过关键案件时间窗。当前实现中阅读期间 `simulation_pulse` 仍会推进时间，后续需按该分流目标增设阅读态门控。
2. **探索与行动态**（移动、开门、搜证、与人物或家具交互）：按动作与路径消耗推进世界时钟与全图 NPC 行动队列。
3. **驻足观察态**（处于场内、未打开阅读/推演界面、原地站立）：提供短暂思考缓冲或受控观察流逝，使玩家可在走廊或房间内驻足观察视野内 NPC 的实时动向。

### 三、 角色移动耗时与防瞬移准则

#### 机制与设计准则

1. **移动与交互的执行顺序**：Godot 宿主中的移动与交互由 `SpatialActionBridge.gd` 与 `DvFieldExecutor.gd` 按阶段信号推进（`approach` 走到 `stand_slot` → `facing` 转向对齐 `face_slot` → 检查 `contact` 接触误差 → 播放 `visual` 动画 → 提交 `dv_complete` 回执）。角色实际到达后才开始下一动作。预计时间耗尽时不得瞬移角色。超时或受阻时返回 `rejected` 回执，保留原位或回滚。
2. **预取消除过门停顿**：通过 `prepare_ahead` 预取下一节点意图并配合 `continuous_walk` 连续通行验证，角色在门洞已开启且令牌有效时可连续跨门，避免每段移动强制减速归零等待确认。
3. **CLI 与 Godot 路径耗时同构**：`GameEngine.EstimateNavigationTravel` 基于真实 Godot `NavigationServer3D` 烘焙路径点计算米制距离，并结合速度上下界交由 `CaseTravel` 估算耗时；建筑发布工具从同一几何源派生导航网格与 DV 房间通行图边长。逻辑时钟按校准后的路径成本记账，实测物理耗时与距离在回执 `field` 中独立记录，确保 CLI 形式验证（及 Lean 证明）与 Godot 实机游玩的时间线一致。

### 四、 门的导航设计建议（NavigationLink3D 双层导航）

当前正式三维路径使用房间连接图和房内路径、碰撞查询，尚不是完整的 `NavigationRegion3D` 网格体系。下面是迁移方案，不表示已经接入。

静态地板、墙体和固定家具参与网格烘焙。门洞两侧网格留出断口，仅由绑定门标识的 `NavigationLink3D` 连接。断口不能被区域边缘自动连接，否则关闭 link 后仍会绕过门状态。门扇作为动态物理碰撞，不随每次开关重烘焙整层。

将两层判断分别保存。Core 的人物路径规划按该人物已知信息判断门是否可用、是否要解锁或开门。Godot 的通行 link 只在客观状态和门扇实际净空允许时启用。闭合但可开启的门仍可成为规划目标，角色先走到门前交互位，提交正式开门意图，等真实开门完成后再穿过。全局 link 不表达每个人不同的钥匙、权限和知识。

门两侧声明接近位、操作位、门槛段和离开位。接近位在门扇扫掠范围之外。开门时先检查扫掠区域，门扇未让出人物胶囊所需净空时不释放通行。关门前检查门槛占用，角色正在穿过时等待或取消关门。双扇门按实际可用净宽判断，旋转门和机关门声明专用动作阶段。

门状态、锁状态或房间连接改变时增加通路版本，使涉及该门的路线失效并重算。网格更新跨物理帧同步后再查询。门变锁不自动写进远处人物认知；未知变化只在真实观察或到门前失败后成为人物证据。窄门需要排队与占用预留，避免双方相向挤压。

`NavigationObstacle3D` 用于局部避让和烘焙输入。单独改变避让障碍不会重写路径连通性，因此不能单独实现锁门阻路。`NavigationLink3D` 的 `enabled` 可以控制路径查询是否使用连接，`enter_cost` 可以表达开门等额外代价；实际开门动作仍由正式会话执行。

参考资料：
- [Godot NavigationLink3D 文档](https://docs.godotengine.org/en/stable/classes/class_navigationlink3d.html)
- [Godot NavigationObstacles 教程](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationobstacles.html)
