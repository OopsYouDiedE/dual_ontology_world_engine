# 《安眠者有福》设计与验收规范

## 当前目标与适用范围

当前制作目标是能实际游玩、能在游戏内录制并用于宣传片的内容片段。地图基础格为 32×32 像素；角色和大型物件可以跨格。完整学园、长期剧情与全部角色属于内容储备，不自动成为当前制作任务。

本文件规定设计过程与完成条件。剧情设定、概念图、旧演出和程序原型均不能单独证明设计完成。具体片段仍须经过以下验证，不能因本规范已写成而标为完成。

当前首宣的“基于真实游戏”首先要求**设计能够在游戏中落实**：明确场景入口、玩家或角色的行动、可取得的信息、实际对象、机制结果与结束状态。剧情镜头可以用游戏内演出组织；展示脑内推演或言灵时必须有真实输入和规则结算。制作阶段再用同一可玩版本的操作、重试与录屏验证，不以概念图、剪辑或预写对白冒充游戏内容。首宣具体范围见[现行宣传片大纲](游戏和核心宣传视频和图片录制/机制主线宣传片大纲.md)；本规范不把二宣的现实规则或群像机制强加为首宣门槛。

每轮先确定一个玩家可见的片段目标、实际入口、本轮要验证的问题及不包含的内容。混合片段分别标出剧情演出与机制结算部分，按各自要求验收。规模按验证问题确定，不把全角色、全动作或完整学园作为单个打样的默认前置条件。规范依据与本次交叉讨论见[设计复盘与裁决](design-retrospective.md)。

## 片段设计顺序

先区分**剧情演出**与**机制切片**。大多数生活、交谈、训练和调查叙事可由 Dialogue 脚本组织对白、选择、走位与专用动作，不要求每段都人为增加游戏规则或失败分支。剧情打样验证入口、人物知情范围、时间线、演出连续性、对白选择与结束后的操作恢复。以下关于行动值、规则因果、错误与重试的要求适用于确实展示机制的镜头；涉及言灵、推演、通路权限等结果时，Dialogue 只表现规则结果，不能代替结算。

1. 明确片段要让玩家理解的一个主要问题、起始处境与可观察信息，注明哪些信息尚未被角色获知。
2. 写清玩家能输入什么、可作哪些选择、行动需要什么条件与代价、如何推进嵌套行动值。NPC 的选择须有其已知信息依据。
3. 给出操作到规则结算再到可见结果的因果链。至少说明一次有效操作和一次有意义的错误、无效操作或不同选择，并说明如何继续或重试。不能为固定剧情强行让正确操作失败。
4. 用可操作原型检查规则和信息反馈，再确定场景构图、资产尺寸及动作需求。
5. 绘制代表性资产并放入实际场景检查。通过后才批量制作同类素材，最后安排镜头与配乐剪辑。

片段记录应直接回答这些问题，可使用短文和示意图，无需为每个步骤制造单独文档或数据类。

推理片段先验证作者的一条完整解释和有意义的因果反例，再扩大资产制作。若设计承诺多解或证据允许其他解释，应检查判定是否误拒这些解释，并如实注明已验证范围；不要求人为给每案增加第二个解。局部换一个搬运者通过，不等于另一条主要因果路线已验证。

玩家应判断证据与行为假设，不必替角色编写重复循环、寻路或迎合不可推知的内部时刻。影响成败的时序条件须有角色可取得的材料或可读反馈支持；内部调度参数与演出计时可以保留。行为组织器可以代做执行细节，但不能替玩家选定未经推断的对象、时机与目的，或把终态直接赋成答案。

## 玩法与表现

宣传日常演出每段默认只安排一至两名主要行动者，其他在场人物保持安静。邀请、接受、让位和回应按先后发生，不为制造热闹让多人同时走位或起坐。只有突发事件确实需要群体反应时才安排同时行动。构图需交代在场人物与完整空间关系，局部动作特写不能代替整个片段和场景的完成验收。

玩家输入必须改变游戏状态或可供判断的信息。结果由实际规则产生，不能由录制脚本、按钮计数或预制动画冒充结算。

现场调查为事件经过提供依据，脑内推理还原驱动人物行动的规则，规则本身就是动机：人物在当时所知的条件下如何选择，获得新信息后如何改变行动。不得另加独立目的字段、动机问卷或评分层。已知事实、历史人物所知、玩家假设与模拟结果分开。玩家编写可组合的人物行为规则，以实际行动与世界规则检验解释，不能直接设置物态、改变现实现场或以新实验替代历史重建。物理重演相容不证明唯一历史，更不自动解锁唯一动机；反馈指出具体差异与缺失依据，不对照作者的唯一动作顺序或人格标签。

词汇允许自由组合，有意义的行动必须能表达，不按人物职业或作者指定分工限制。行动能否完成取决于实际位置、知识、工具、对象状态和能力；同一目的可采用不同办法，同一动作可服务不同目的。人物只能依据当时可取得的信息决策，不能继承侦探后来调查或广播取得的知识。合法动作的失败保留为实际后果；有意义但尚未实现的组合须列为能力缺口，不能判为玩家推理错误，也不能以列出缺口冒充完成。保留直接编辑，词库帮助表达而不替玩家选解；不得强制提交两套答案才允许通关。初醒的具体决策与验收见[动机还原设计](academy_setting/first-awakening-design.md)。人物行动语言与言灵分开，言灵的挑战来自目标、范围、时机与位格，而非无目的增加语法。

言灵输入必须符合片段定义的道本语（受限方言）词汇、词序与句法。中文释义和自然语言叙述可以帮助理解，但不能作为咒文输入或替代可解析句子；解析后的规则结果仍须由 Core 结算，句法成立不等于目的达成。

操作反馈须让玩家看见行动对象、发生的变化及角色可知的失败现象或依据，并能判断下一步如何继续。隐藏原因可以保持未知，不能把内部失败码直接翻译成角色尚未取得的秘密。可调查对象应能被发现、接近并可靠选中；人物与器物重叠、遮挡或输入焦点不得使必要调查只能靠猜像素完成。反馈区分未调查、已知证据不相容与当前尚未模拟完成，不以差异数量制造已通关的假象。

涉及 Core 行动值或案件因果的结果，由对应规则阶段结算；纯剧情和游戏层交互按其实际状态机处理。动画可以有接触与特效事件，播放速度和剪辑节奏不改变行动值规则。涉及规则结果的动作须检查所支持的中断、跳过或重播不会提前、遗漏或重复结算。动作验收室可以用局部事件改变演示物件表现及碰撞，但这只证明表现联动，不证明正式案件结算。剧情演出结束后必须能回到明确的可操作状态。

机制片段按实际交互说明权威状态及边界：Core 的空间归属或抽象可达不等于房内几何可达；游戏层负责距离、通行、碰撞与需要的感知筛选。客观房间子树不会自动成为人物知识，身份关联也不能由投影存在直接推定。涉及这些问题时，记录感知取得、主体决策、客观结算与反馈的来源，复用当前源码与对象引用；不为满足记录要求新建通用接口、重复状态或平行对象系统。Core 具体维护约束见 [csharp/AGENTS.md](../csharp/AGENTS.md)。

每个录制段注明实际入口、准备操作和取景区间。允许剪辑与标题包装；镜头依赖的交互和前后状态必须能在同一可玩版本中复现。不得只制作机位内的假门、假通路或无法操作的关键器物来替代玩法。

## 32px 像素制作

地图以 32×32 基础格拼接。角色采用 32×48 像素的基础帧规格；这是角色帧尺寸，与 32×32 地图格不是同一概念，角色可以跨越一个地图格的显示高度。先定俯视角度、墙高、地面基线和角色相对门桌的尺度，再绘制房间。图像画布尺寸、地面占地和遮挡范围分别说明，不能用画布矩形直接代替碰撞。

### 人物统一制作规格

首批动作v2采用64×64统一运行时承载格，将普通人形的32×48设计范围放在透明留白中，供伸手、挥击和施法使用；不是把人形放大到64px。该图集锚点为(32,55)，居中节点偏移(0,-23)，正常人形约43px高，地面占位与碰撞仍遵循下表。32×48原生帧的锚点(16,47)不可直接套到这份扩展图集。详见[运行时图集说明](../godot_csharp/ShareAsset/Internal/Characters/animation_v2/README.md)。

32×32是本项目选定的地图尺度，不是所有或大部分RPG必须遵守的行业标准。人物使用独立精灵帧，不称为“人物tile”。正常人形采用以下规格：

| 项目 | 统一要求 |
| --- | --- |
| 地图基础格 | 32×32px |
| 站立与普通行走的基础设计画布 | 32×48px，透明底；人物按此尺度以1倍显示。运行时可放入更大的透明承载格，当前v2为64×64，不放大人形 |
| 正常站立的地图占位预算 | 1×1格，即32×32px地面区域；不是1×1.5格的地面占地 |
| 基础设计画布的显示跨度 | 1格宽、1.5格高；扩展承载格另计透明留白。上半身可遮住脚底后方的格子，不阻挡该格 |
| 32×48基础帧的地面锚点 | 帧坐标(16,47)，表示第46行脚底像素的下边缘；最后一行透明。扩展帧使用其登记锚点 |
| 连续移动的基础碰撞盒 | 16×12px，中心相对锚点(0,-6)，即x∈[-8,8)、y∈[-12,0)；由游戏层负责 |
| 遮挡排序点 | 地面锚点的Y值；头顶、帽顶不参与地面排序 |
| 基础朝向与动作 | 手绘前（朝屏幕下）、后（朝屏幕上）、左三向；右向由左向水平镜像。当前宣传前三场角色采用侦探v2系列；动作设计参考见[首批人物动作设计](character-actions.md) |

占位预算用于地图布置；连续移动时不把角色锁在格中心，碰撞盒可能跨过相邻格边界。若玩法需要离散占格，另以脚底位置归属1格，不从精灵矩形推算。普通门口净通行宽度至少32px；双人并行通道按64px规划。人物互挡、对话距离和触发区是独立规则，不随图片透明边自动变化。

Godot中以角色根节点作为地面锚点；居中Sprite2D使用offset=(0,-23)，或不居中时使用offset=(-16,-47)。当前旧摆景以Sprite中心定位，迁移时保持脚底世界位置再调整父节点，不能只改offset使人物整体跳位。碰撞盒与这些偏移是统一制作目标，现有摆景不因此自动获得移动和碰撞实现。

人体目标轮廓宽18–26px、高38–46px，发型、裙摆可在画布内扩展，但须保持脚底和透视。采用略俯视的约3头身轮廓；不同身高通过留白体现，不缩放节点。禁止把所有角色画到相同外接框来假造一致性。衣着遵循角色资源目录的年代与随身物品约束。

转身、步行时支撑脚落点稳定，身体允许设计内的1px起伏；携带、坐姿、倒地和施术另列动作。超框动作可用64×64或64×96扩展画布，逐帧记录同一地面锚点；扩大图片不自动扩大占格或碰撞。不可裁掉伸出的手臂，也不可缩小整个人塞回32×48。阴影和选中圈单独绘制，默认不烘入人物。

人物共享规格在正式扩产前用代表角色验收：同时显示画布框、32px地面格、脚底锚点和碰撞盒，检查静止、四向步行、32px门口、墙角、桌后遮挡及两人错身；角色1倍原图与2/3/4倍最近邻显示均须可读。具体片段按实际用到的朝向、动作与空间交互验收，不为只出镜站立的角色补齐全套动作。21人身份资源以正面待机帧为基准；当前宣传前三场另有九名角色的v2基础动作，尺寸合规不等于动作与实机通过；源稿经缩放整理的资源仍应如实标明派生过程，不称为逐像素原绘。

资产在制作前确定源文件与像素尺寸，并按用途确定锚点、朝向、动作帧需求、遮挡层和交互位置；静态装饰无需制造不存在的动作或交互字段。角色脚底锚点在同一动作中稳定，跨格物件必须留出实际通行和操作位置。

同一资产族在其 README 或既有清单中记录源稿、转换入口、派生资源和实际引用场景即可，不必每张图另建表。源尺寸、基础设计画布与运行时承载格分别写明。更换规格或生成入口时核对项目配置、场景引用和重建输出，避免旧脚本覆盖新资源。授权与原创源的保留要求不因派生产物弃用而消失。

美术生产源与运行时资产分别归 `godot_csharp/AssetsSource/` 和 `godot_csharp/ShareAsset/`，具体分类见[游戏层路径规范](../godot_csharp/AGENTS.md)。源区不参与 Godot 导入；实际加载的纹理即使不需加工，也由生产链路复制到运行时区。目录迁移不改变像素、帧规格、锚点或碰撞；须检查同名冲突、资源内部依赖与重建入口，并在重建后验证受影响场景，不能只以 C# 编译通过判定完成。

以原生像素检查轮廓与色块，再以游戏实际显示倍率检查可读性。像素图采用最近邻采样；世界画面避免非整数缩放造成像素粗细变化。文字界面的分辨率与布局单独验证，不要求字体强行按地图格绘制。

调整人物在屏幕中的视觉大小时，统一调整整个游戏世界的显示倍率：角色、地面格、家具、门窗与其他场景物件保持同一倍率。不得单独缩放角色精灵或改变人物相对地图的比例来解决取景问题。倍率变化会改变屏幕可见的世界范围，因此须复核通路、交互距离、遮挡和构图；世界坐标、地图格尺寸、碰撞与地面占位不因镜头缩放而改变。

角色靠轮廓、服装大色块和姿态区分。空手前站帧只是身份基准，不代表所有动作已经完成；动作帧应按实际片段另行制作和验收。徽记在地图尺寸下使用可辨识的简化图形，完整纹章用于足够大的载体。细节、光照和动画不得掩盖可交互对象及状态变化。

48px 外部素材的原生切片尺寸仍按源素材读取。把 TileSet 参数改为 32 或整体缩小图片不能算完成迁移；需检查轮廓、接缝、比例、遮挡和动画一致性，必要时重绘。旧母版未经此验证不得称为当前标准资产。

正式扩产前，至少把片段中的角色与关键物件放在一段含门、墙角和遮挡的实际地图中，验证移动、交互及状态变化。局部截图只证明被检查部分，不代表整套资产通过。

## 完成条件

剧情打样：可从明确入口观看并操作，Dialogue 分支、走位与所需动作可重现，结束恢复操作；审美与人物演技待用户审看。首个样片通过前，不自动扩产全部角色和镜头。纯演出不以嵌套行动值驱动；游戏层实时表现与 Core 规则职责保持分开。

设计稿：玩法因果和制作规格已写清，未经过实机验证。

可玩原型：从入口经真实输入可以得到预期结果，错误与重试可验证；占位图允许存在，不能称为美术完成。

制作验收：资产可编辑、可重复导入，32px 场景内比例与遮挡正确，所需动作连续可读，实际操作不会因取景安排受阻。

片段完成：可从明确起点完整游玩并重试，关键规则经代码检查和针对性验证，实机录制能解释玩家操作与结果。记录验证命令、结果和未解决限制。任一必要项未通过，仍为制作中。

验收记录注明日期、实际入口、被检查的版本或工作区状态、操作/命令、观察结果与限制；已有场景 README 和验证输出足够，不要求新增报告体系。构建只证明可构建，尺寸与帧数检查只证明结构，截图只证明所示画面，局部操作只证明相应路径。技术通过、审美待审与玩法待验证应分别陈述，不能合并为“全部完成”。

推理体验须由未读谜底的试玩检查可发现性、假设形成、表达负担和修改动机。记录提示条件与停止位置；中途收尾不能证明最终不可解，也不能称为整案通关。修复后的回归结果另记，不改写原试玩成绩。AI 试玩可发现问题，工具耗时不能当作人类游玩时长，也不能据此宣布乐趣或时长目标达成。只验证本片段需要的内容；纯剧情、概念稿、单件装饰不强加整案或全动作验收。

## 文档与工作分配

README 负责入口和当前状态；本文件负责设计与验收；设定文档负责世界与内容；场景 README 负责操作和验证；插件 README 负责资源导入。相同规则只维护一处，其他位置链接。

AGENTS 只记录项目已经发生的问题及避免复发的具体约束。旧版本产物不能充当新设计依据；删除前检查引用和源文件关系，保留仍有用途的原创源素材与授权信息。

常规盘点、去重、引用修复和明确规格下的制作交给低成本子代理。涉及复杂玩法因果、艺术语言或相互冲突的设计由主代理接手；无法由已确认约束推出的方向问题交用户决定。
