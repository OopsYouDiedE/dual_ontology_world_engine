# UI 与场景系统拆分设计

本文以功能闭环定义当前设计的一级系统、二级验收边界与 Godot 内置能力。系统设计不等于实现完成；源码映射、实施进度和测试结果记录于 `33 实施与验收.md`。机器可读契约见 `tools/report/functional_systems.json`。

## 一、划分原则

- 一级系统对应稳定的功能闭环，二级系统对应可分别观察和归因的职责。不按按钮、节点类型或脚本数量机械拆分。
- 保留五个 UI 系统：脑内推演、GUI、音效、标题、游戏暂停／书 UI。音效归 UI 组管理，提供全项目共享服务。
- 场景分为八个系统：建筑结构生成、家具生成、房间修建、角色控制、角色验收、角色表现、房间运行、镜头与环境呈现。
- “角色验收系统”专指测试与证据采集，独立于生产角色控制和角色外观动画。不建立第二套角色/世界状态。
- 原先 16 个模块是代码归属参考；本设计是功能和验收主视图。一个现有协调脚本可能服务多个功能系统，不能因此把这些系统重新合并。
- Core 保留客观事实、人物认知、推理、规则与时间的权威。UI 消费授权观察并提交意图；场景报告真实执行结果。人物、规则与初始布置通过 DV 声明。

## 二、UI 五个一级系统

| 系统 | 二级验收系统 | 输入与输出 | 边界 |
| :--- | :--- | :--- | :--- |
| **UI01 脑内推演 UI** | 证据浏览；规则/前提/目标呈现；推演操作区；提交与结果反馈 | 授权推演预览 → 动作/证据 ID 提交意图 | 草稿只在 UI 内；证明、认知变更和证据时效由 Core 校验 |
| **UI02 GUI／现场 HUD** | 时间地点状态；任务进度/取消；目标/动作菜单；对话/说服反馈；引导/需求/控制提示 | 只读 interface、屏幕锚点 → 玩家操作意图 | 不另建时钟；进度条或对话演出结束不直接决定动作成功 |
| **UI03 音效与音乐** | UI 操作音；世界空间音；配乐/环境上下文；总线/并发/设置；暂停/跨场景/退出 | 声音事件、位置与公开音乐上下文 → 播放/混音/停止 | 覆盖整个项目；播放出来的声音不自动等于人物听到的证据 |
| **UI04 标题界面** | 菜单可用性；标题输入/焦点；新局/继续/退出转场 | 存档可用性与输入 → 模式切换意图 | 不自行创建第二个会话；3D 书房背景由 SC08 提供 |
| **UI05 暂停／书 UI** | 开合/暂停请求；书页/内容导航；3D 书页输入；存档读档界面；设置/语言/可读性 | 公开槽位/设置/舞台映射 → 暂停、翻页、存取与设置意图 | 2D 页面和输入归 UI；3D 书叶/镜头归 SC08；真实存取归会话 |

### UI01 的进一步边界

脑内推演需要独立验收“证据是什么”“玩家选择了什么”“Core 判定了什么”。证据的已知/未知/冲突状态不可混用；不能因为 UI 没显示某条证据就当它为假。列表式与图形式工作台共用同一提交契约，不在前端复制推理器。图形连线、拖拽等可以作为操作区的实现，不必各列一个一级系统。

### UI02 与世界标记的分工

GUI 管理目标菜单和屏幕投影；角色头顶物体的世界姿态由场景负责，GUI 只消费公开锚点。动作选项必须来自最新合法观察，目标失效、场景切换和模态打开时清理过期菜单。说服界面只能展示已送达内容与公开原因，不展示对方私有权重。

### UI03 的声学分层

1. 播放层使用 Godot 播放器、音频总线和效果。
2. 项目呈现策略选择音乐、声音事件、并发、空间监听和暂停行为。
3. Core 决定通信路径、角色能否听见/辨认、信息来源和证据。

这三层分别验收。空间衰减不自动包含隔墙/跨门的声学规则；隐藏场景节点也不自动关闭声源。需要声音效果的用例必须保留实际音频观察，不能只以“播放器已调用”判通过。[Godot Audio buses](https://docs.godotengine.org/en/stable/tutorials/audio/audio_buses.html)、[AudioStreamPlayer3D](https://docs.godotengine.org/en/stable/classes/class_audiostreamplayer3d.html)。

### UI05 与暂停范围

“书已打开”只是页面状态。暂停协调必须明确冻结哪些 Core tick、物理移动、动作队列和动画，哪些书页动画、菜单声音或背景音乐允许继续。多个弹层或其他暂停原因同时存在时，只解除本次申请，最后一个原因解除才恢复世界。该规则是当前设计契约，不宣称已有暂停 token 公共接口。

Godot 提供 `SceneTree.paused` 和 `Node.process_mode`，项目仍要协调独立的 C# 仿真调用。具体实现可以使用分支暂停或场景树暂停，但须满足同一份行为契约。[Godot 暂停与处理模式](https://docs.godotengine.org/en/stable/tutorials/scripting/pausing_games.html)。

UI05 输出书页纹理并接收舞台映射；屏幕坐标、书页 UV、子视口坐标、翻页锁输入和鼠标穿透单独验收。独立 `SubViewport` 默认不会自动收到输入事件。[Godot SubViewport](https://docs.godotengine.org/en/stable/classes/class_subviewport.html)。

## 三、场景八个一级系统

| 系统 | 二级验收系统 | 主要产物／边界 |
| :--- | :--- | :--- |
| **SC01 建筑基本结构自动生成** | 坐标/单位/参数；结构重建；门窗洞口/接缝；碰撞/导航源元数据；材质/剖切预览 | 参数 → 建筑网格、碰撞与结构元数据；不包含编辑工具交互 |
| **SC02 家具与交互物件生成** | 目录/实例装配；尺度/材质/碰撞；站位/触及/座位；物件动作/逻辑绑定；候选保存/发布校验 | 原子资产/配置 → 智能预制件；原始模型制作和 AI 生成归资产制作流程 |
| **SC03 可视化房间修建** | 拾取/工具模式；变换/吸附/ghost；放置合法性；撤销重做；候选持久化；明确发布/DV 一致性 | 调用 SC01/SC02 编辑房间，不复制生成算法 |
| **SC04 角色控制器** | 意图/队列；路径跟随/物理移动；到达/转向/对齐；工作/取消/失败；跨房/真实计时 | 合法意图 → 真实执行与回执；不直接写世界事实 |
| **SC05 角色验收与测试** | 用例/覆盖；体型净空；位移速度/动画；坐姿触及；取消/多人；报告证据 | 正常操作与观察 → 测量和断言；不提供绕过规则的生产角色测试 API |
| **SC06 角色外观、动画与姿态** | 模型骨架装配；移动动画过渡；行为/对话演出；坐姿/触及骨骼修正 | 消费运动和动作阶段，输出可见姿态；不拥有第二个运动主权 |
| **SC07 房间运行、门窗与空间连接** | 加载驻留/卸载；门窗状态/碰撞；导航/跨房连接更新；空间注册/交互端口 | 运行已发布房间；与修建工具和 Core 逻辑空间分别验收 |
| **SC08 镜头、书房舞台与环境呈现** | 镜头/模式交接；3D 书叶/纹理映射；遮挡剖切/可读性；环境材质/性能 | 基于正式时间和模式呈现，不推进世界或替代逻辑视听 |

### SC01、SC02、SC03 的职责链

`房间编辑命令 → 结构/家具生成 → 候选房间 → 保存与重载校验 → 明确发布 → 正式房间运行`。

SC01 拥有结构参数到几何的转换；SC02 拥有家具配置到智能预制件的转换；SC03 负责选择、摆放、撤销、保存、合法性检查和发布。禁止三处分别实现一套墙体或家具生成代码。

编辑器前端可使用 `EditorPlugin`、gizmo 与 `@tool`。运行时修建前端不得依赖导出游戏中不存在的编辑器 API。编辑器撤销接 `EditorUndoRedoManager`，运行时使用 `UndoRedo` 或项目命令栈；二者可共享命令数据和验证规则。[EditorPlugin](https://docs.godotengine.org/en/stable/classes/class_editorplugin.html)、[EditorUndoRedoManager](https://docs.godotengine.org/en/stable/classes/class_editorundoredomanager.html)。

候选保存必须包含必要的 owner、碰撞、锚点、实例 ID 与资源依赖。`add_child` 不等于子节点一定被场景打包保存。[PackedScene](https://docs.godotengine.org/en/stable/classes/class_packedscene.html)。

发布流程须确定布局的作者源，发布后场景与 DV 绑定一致；不允许 `.tscn`、`.dv` 和宿主脚本各维护一套可自由修改的初始布置。内容重载保留运行状态/证据；需要初始化的修改明确要求新局。

### SC04、SC06 与 SC05 的三分

- SC04 是执行者，负责实际身体运动、对齐与工作完成。
- SC06 是表现者，负责动画、模型、姿态和演出回调。
- SC05 是观察和验收者，负责按正常公开操作采样、测量和判定。

导航查询与真实移动必须分别验收。Godot 导航系统提供路径/跟随计算，不自动移动角色父节点；现有直接使用 NavigationServer 的实现也无需为了模块命名被强制改成 NavigationAgent。[Using NavigationAgents](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationagents.html)。

物理位移保持单一主权。若采用动画 root motion，提取的增量交给 SC04 显式消费，不让动画和马达同时修改身体位置；撞墙时不能靠循环步行动画伪装运动。[CharacterBody3D](https://docs.godotengine.org/en/stable/classes/class_characterbody3d.html)、[AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)。

### SC05 的角色验收矩阵

| 维度 | 验收范围 | 证据与判定 |
| :--- | :--- | :--- |
| 正式角色差异 | 实际声明的体型、胶囊、骨架和动作集 | 角色/内容 ID、尺寸来源；不注入临时测试参数 |
| 通行与阻挡 | 正式门洞、楼梯、坡面、窄处、静态/动态阻挡 | 真实位移、接触/碰撞和房间观察；不做开发传送 |
| 速度与时间 | 正常、游戏加速、暂停、恢复 | 实际距离/物理秒与世界时钟分别记录 |
| 姿态与接触 | 入座/离座、转向、触及、物件动作 | 接触误差、锚点、动作阶段与实机图；阈值来自内容/绑定 |
| 生命周期 | 取消、打断、目标失效、跨房 | 原始失败/完成回执、资源释放和执行代际 |
| 多人 | 门口相遇、座位/站位争用 | 容量、阻断、重选和占用释放证据 |

验收使用正式人物与正式新局。没有自然可达条件的用例记未覆盖；不创建隐藏测试人偶、临时测试工程、合成端点、状态注入或伪造回执。作者预览可用于检查资产尺寸，但不能替代正式宿主玩法验收。

## 四、共享支撑职责

| 契约 | 所有权和职责 |
| :--- | :--- |
| **A01 模式、输入与暂停协调** | 协调标题/现场/书本/推演/修建模式、焦点、防穿透和暂停原因；各系统只发请求，不直接互相操作内部字段 |
| **A02 会话观察与操作网关** | 复用 Main/SessionBridge 公共接口；授权只读观察、动作意图、真实完成证据和存取服务；Core 权威保持唯一 |
| **A03 内容与资源契约** | 坐标/尺度、稳定 ID、结构/预制件版本、锚点/碰撞层、候选/发布、资源引用与 DV 初始化 |
| **A04 真实宿主证据流程** | MCP 启停/正常输入观察、期限与原始回执保管；SC05 选择角色用例，不复制测试宿主基础设施 |

这些是支撑职责，不要求再增加四个包办业务的全局 Manager。实现变化时更新 `31 系统架构与核心机制.md` 第五节接口表；本设计不增加未经实现的公共 API。

## 五、Godot 已内置，但仍需项目整合验收的能力

| 内置能力 | 项目仍需实现/配置并验收 |
| :--- | :--- |
| Control、Container、CanvasLayer、Theme | 界面状态、布局、主题应用、焦点、模态、滚轮/点击穿透 |
| SubViewport、ViewportTexture | 3D 书页纹理与坐标映射、输入转发和翻页同步 |
| SceneTree.paused、Node.process_mode | Core/物理/动作/动画/音频的暂停范围和恢复条件 |
| AudioServer、总线、AudioStreamPlayer(3D) | 声音事件、选曲、并发、空间监听、暂停和资源释放 |
| ArrayMesh、SurfaceTool | 结构拓扑、洞口、尺寸和网格/碰撞/导航源一致性 |
| PackedScene、ResourceLoader/ResourceSaver | owner、稳定 ID、候选/发布、内容版本和 DV 一致性 |
| EditorPlugin、gizmo、@tool | 建造工具模式、编辑命令与编辑器/运行时分离 |
| EditorUndoRedoManager、UndoRedo | 正确的命令事务、引用寿命与编辑器/运行时历史 |
| CharacterBody3D、形状和物理查询 | 速度、层/掩码、坡阶参数、阻断恢复、动作阶段 |
| NavigationServer、NavigationAgent、NavigationRegion | 数据同步、物理跟随、门连接、到达/失败判定 |
| AnimationPlayer、AnimationTree、Skeleton3D | 动作映射、token、姿态、触及与运动主权 |
| Camera3D、Environment、灯光和场景树 | 镜头/剖切/风格、驻留、资源/性能策略 |

不另行自研布局、物理、导航、动画、混音或渲染引擎。内置不等于项目功能自动完成，也不等于可以跳过整合验收。上述 API 是能力选项，不表示仓库已经采用全部节点。

## 六、一级闭环与验收规则

1. **暂停书本闭环**：现场动作 → UI05 → A01 暂停 → SC08 书页/镜头 → UI03 菜单声 → 返回；验证世界没有偷跑、输入不穿透、其他暂停原因未误清除。
2. **推演闭环**：UI02 引导 → UI01 选择证据 → A02/Core 校验 → 正常反馈；验证本人证据、草稿不提交、无隐私泄漏。
3. **房间制作闭环**：SC03 → SC01/SC02 → 候选保存重载 → 明确发布/DV 校验 → SC07；验证内容和几何/碰撞/导航绑定一致。
4. **角色交互闭环**：UI02 → A02 → SC04 到达/对齐 → SC06 姿态 → 家具/门窗 → Core 完成 → SC05 记录；按同一 execution 关联真实证据。

二级用例验证单一职责，一级用例验证协作闭环。正式测试走 `Main.tscn` 和真实 CLI/Godot 新局；自动测试设置期限并全程连接，AI/人工按最新观察串行操作并最终关闭。PASS、FAIL、未覆盖分列；超时、静态扫描或预览不能代替玩法通过。

每项记录系统/二级系统/用例 ID、backend、代码/内容版本、seed、run、角色/物件/执行标识、前观察、正常操作、后观察、预期、实测、阈值来源、结论、回执/截图路径与覆盖限制。
